## 2. Test design — why the results are unambiguous

The CCP agent's built-in defaults (from
`otelcollector/shared/configmap/ccp/tomlparser-ccp-default-scrape-settings.go`) are:

```go
config["controlplane-apiserver"]               = "true"
config["controlplane-cluster-autoscaler"]      = "false"
config["controlplane-node-auto-provisioning"]  = "false"
config["controlplane-kube-scheduler"]          = "false"
config["controlplane-kube-controller-manager"] = "false"
config["controlplane-etcd"]                    = "true"
```

Every scenario deliberately sets values **flipped away from these defaults**, so that "the
ConfigMap was honoured" and "the agent silently fell back to defaults" produce *different,
observable* outcomes in the AMW. A test that merely re-stated the defaults would prove nothing.

| Scenario | apiserver | etcd | kube-scheduler | kube-controller-manager |
|---|---|---|---|---|
| **Defaults (no ConfigMap)** | true | true | false | false |
| 1 — v1 | true | **false** ⬅flipped | **true** ⬅flipped | false |
| 2 — v2 complete | true | true | false | **true** ⬅flipped |
| 3 — v2 incomplete | **false** ⬅flipped | true | **true** ⬅flipped | false |

Only reliably-present control-plane targets were used (apiserver, etcd, kube-scheduler,
kube-controller-manager). `cluster-autoscaler` and `node-auto-provisioning` were left disabled
because those workloads are not guaranteed to run on the test cluster.

### Discriminating metrics

Each job was probed with a metric that is **unique to that job** within the CCP minimal
ingestion profile keep-lists:

| Job | Probe metric | Why unique |
|---|---|---|
| `controlplane-apiserver` | `apiserver_request_total` | only in apiserver keep-list |
| `controlplane-etcd` | `etcd_server_has_leader` | only in etcd keep-list |
| `controlplane-kube-scheduler` | `scheduler_schedule_attempts_total` | only in scheduler keep-list |
| `controlplane-kube-controller-manager` | `workqueue_depth` | only in KCM keep-list |

> `rest_client_requests_total` was deliberately **not** used — it appears in the etcd,
> cluster-autoscaler *and* KCM keep-lists and would be ambiguous.

## 4. Isolating our signal from cx-1's own control plane

⚠️ **Gotcha worth documenting.** Because `CLUSTER` is set to the cx-1 resource ID, our agent
emits series with `cluster="standalone-260805w9xxil-cx-1"`. But cx-1 is itself a real AKS
cluster, and enabling the addon on it caused **cx-1's own managed control plane** to emit
`controlplane-*` series under the **exact same `cluster` label**. The only distinguishing label
is `instance` (the scraped pod name).

Two mitigations were applied:

1. **Attribution by pod identity.** Every query result is classified as *ours* vs *foreign* by
   matching `instance` against the live pod list of our CCP namespace
   (`6a7393d0e6eaaf00013c8824`). See `Verify-Scenario.ps1` logic described in §7.
2. **Silencing the foreign source.** A ConfigMap was applied to **cx-1's own** `kube-system`
   disabling all `controlplane-*` targets for cx-1's own CCP agent. After this took effect the
   *foreign* column dropped to `0` for the remainder of the run.

Evidence of both sources co-existing, captured during Test 1 before the silencing took effect:

```
JOB                                    OURS         FOREIGN (cx-1's own control plane)
controlplane-apiserver                 2            6
controlplane-etcd                      0            3
controlplane-kube-scheduler            1            0
```

`OURS` = `kube-apiserver-647b55d46f-*` (our CCP ns). `FOREIGN` = `kube-apiserver-6b7966dcd6-*`
and `etcd-6a7386d081b39e0001642494-*` (a *different* CCP namespace = cx-1's own control plane).

A pre-test baseline confirmed the AMW had **no** `controlplane-*` jobs at all before our agent
started:

```
{job=kubelet} => 8        {job=cadvisor} => 8       {job=node} => 8
{job=networkobservability-retina} => 8              {job=kube-state-metrics} => 1
```

### Test 3 — **incomplete v2** ConfigMap (PR #1582 regression test)

ConfigMap: [`configmaps/03-v2-incomplete.yaml`](configmaps/03-v2-incomplete.yaml) · verified twice (see below)

#### What is being tested

For `schema-version: v2`, the CCP parser reads **two** projected files:

```go
filePaths := []string{
  "/etc/config/settings/controlplane-metrics",
  "/etc/config/settings/prometheus-collector-settings",
}
metricsConfigBySection, err = shared.ParseMetricsFiles(filePaths)
```

This ConfigMap **deliberately omits the `prometheus-collector-settings` data key**, so the second
file does not exist. Confirmed on the live ConfigMap — only three keys present:

```
config-version
controlplane-metrics
schema-version
```

* **Before PR #1582:** a missing file returned an error from `ParseMetricsFiles`, the whole v2
  config was discarded, and the agent logged *"Failed to parse v2 settings … Falling back to
  default configuration"*.
* **After PR #1582** (`shared/helpers.go` → `parseMetricsFileInto`): a missing file is skipped as
  an optional section and the rest of the v2 config still applies.

The fix is present in this image — verified at the release commit:

```go
// parseMetricsFileInto parses one config file into the section map. A missing file is
// skipped (omitted optional section); only other open/read errors are fatal.
if os.IsNotExist(err) {
    log.Printf("info: optional settings section %q not provided (file %s); using defaults", ...)
    return nil
}
```

#### Did it take the ConfigMap values instead of the defaults? — **Yes.**

**(a) The agent explicitly reports loading from the ConfigMap, not defaults**

```
ConfigureDefaultScrapeSettings::Loading settings from config map
```

(The defaults path would log `ConfigureDefaultScrapeSettings::Loading default settings`.)

**(b) The missing optional section is handled gracefully**

```
info: optional settings section "prometheus-collector-settings" not provided
(file /etc/config/settings/prometheus-collector-settings); using defaults
```

**(c) No fallback / config-dropped markers anywhere in the logs**

Searched for `Failed to parse v2 settings`, `Falling back to default configuration`,
`Continuing with default configuration`, `Invalid schema version or no configmap present. Using
defaults`, `Loading default settings` → **none found**.

**(d) Final effective settings equal the ConfigMap, NOT the defaults**


## 6. Issues found during validation

None of these are defects in `prometheus-collector`, but all three blocked validation and are
worth tracking.

### 6.1 `e2e-ssl` DaemonSet is broken on Ubuntu underlays (standalone infra) — **highest impact**

`e2e-ssl` writes the E2E CA to the Mariner/RHEL anchor path and then runs `/usr/bin/update-ca-trust`:

```
msg="wrote certificate" filename=/etc/pki/ca-trust/source/anchors/hcprz5v2hyk5-hcp-api-eastus2-certificate.pem
msg="failed to update trust store" error="fork/exec /usr/bin/update-ca-trust: no such file or directory"
```

But the cx-1 nodes run **Ubuntu 20.04.6 LTS**, which uses
`/usr/local/share/ca-certificates` + `update-ca-certificates`. The DaemonSet CrashLoopBackOffs on
every node, so the E2E CA is never trusted. Cascade:

```
e2e-ssl fails → E2E CA not in node trust store
  → etcd-connector cannot verify etcd-backup-proxy TLS
     ("x509: certificate signed by unknown authority")
  → backup sidecar cannot get an MSI token → fatal
     → etcd operator's disaster-recovery cannot check for a backup → 0 etcd pods
        → kube-apiserver CrashLoopBackOff → cluster stuck in "Creating" indefinitely
```

**Workaround applied** — a small privileged DaemonSet on cx-1 that copies the staged anchors into
the Ubuntu path and runs `chroot /host /usr/sbin/update-ca-certificates`. After restarting
`etcd-connector`/`msi-connector` and the backup sidecar, etcd came up with 3 members, the
apiserver recovered, and the cluster reached `Succeeded`.

> This should be raised with the standalone / e2e-ssl owners — any CCP validation on an Ubuntu
> underlay will hit it.

### 6.2 `aksdev` cannot authenticate on Windows

Two independent causes:

1. `go-autorest`'s `NewAuthorizerFromCLI` **overrides `PATH`** with hardcoded Azure CLI install
   paths, checking `%ProgramFiles(x86)%\Microsoft SDKs\Azure\CLI2\wbin` (wrong dir for a 64-bit
   install) and a second entry with a leading space. Result: `'az' is not recognized`.
   **Fix:** set `AzureCLIPath=C:\Program Files\Microsoft SDKs\Azure\CLI2\wbin`.
2. `toolkit/devinfra/armclients/clientprovider.go` only registers `AzureCLICredential` if
   `/bin/sh` exists — a Unix-only probe that always fails on Windows, so it demands
   `AZURE_CLIENT_ID`/`AZURE_CLIENT_SECRET`:
   ```go
   if _, err := os.Stat("/bin/sh"); err == nil {
       cliCred, err := azidentity.NewAzureCLICredential(nil)
   } else {
       logger.Warn("AzureCLICredential skipped due to \"bin/sh\" not found")
   }
   ```
   **Fix:** create an empty `C:\bin\sh` stub. (`azidentity` itself handles Windows correctly via
   `cmd.exe`, so the probe is the only blocker.)

### 6.3 Reconcilers revert the patched deployment — skill doc is incomplete

The skill lists four reconcilers to scale to 0. That is **not sufficient**: `eno-controller`
(namespace `eno-system`) restores `eno-reconciler`, which then reverts `ama-metrics-ccp` back to
the chart-default image (`7.1.0-main-07-07-2026-548e23dc-ccp`) and the overlay `CLUSTER` value.
This silently invalidated a test run mid-flight.

Full set that must be scaled to 0:

```bash
kubectl scale deploy eno-controller eno-reconciler -n eno-system --replicas=0
kubectl scale deploy addonconfigreconciler -n addonconfigreconciler --replicas=0
kubectl scale deploy overlaymgr-overlaymanager overlaymgr-overlaymanager-loop -n overlaymgr --replicas=0
kubectl scale deploy eno-reconciler -n <CCP_NAMESPACE> --replicas=0   # per-CCP reconciler
```

The `skip-ccp-reconcile-until-this-time` namespace annotation alone did **not** prevent the
revert. A self-healing watchdog that re-asserts the patch on drift is recommended for any run
longer than a few minutes.

### 6.4 Skill doc: use `ciprod`, not `cidev`, for released tags

The skill says to use `cidev`. When validating an already-released tag from `RELEASENOTES.md`,
the image lives under `ciprod`. Both the registry path and the `-ccp` suffix matter.

## 7. Reproducing

ConfigMaps used are in [`configmaps/`](configmaps/). `00-cx1-silence.yaml` is applied to the
**cx-1 underlay's** `kube-system`; the numbered ones to the **overlay cluster's** `kube-system`.

```powershell
# apply a scenario to the overlay cluster
kubectl delete configmap ama-metrics-settings-configmap -n kube-system --kubeconfig overlay.kubeconfig
kubectl apply -f configmaps/03-v2-incomplete.yaml --kubeconfig overlay.kubeconfig

# force a clean re-parse (parser runs at container start after a 30s settle)
kubectl delete pod -n <CCP_NS> -l rsName=ama-metrics-ccp --kubeconfig cx-1.kubeconfig

# parse-level evidence
kubectl logs deploy/ama-metrics-ccp -c prometheus-collector -n <CCP_NS> --kubeconfig cx-1.kubeconfig \
  | Select-String "SCHEMA_VERSION|Processing v|Final scrape settings|Loading settings from config map|optional settings section|Failed to parse|Done merging"

# ... wait >= 15 minutes, then query the AMW
```

AMW queries use the workspace's Prometheus endpoint with an AAD token for
`https://prometheus.monitor.azure.com`:

```
GET {prometheusQueryEndpoint}/api/v1/query?query=<promql>
Authorization: Bearer <token>
```

> ⚠️ The AMW query API requires **exactly one metric name** per query — bare label-matcher
> queries such as `count by (job) ({job=~"controlplane-.*"})` are rejected with
> `Bad Request: No metric found. Exactly one metric name must be specified.` Use
> `up{...}` or a concrete metric name.

Attribution of a returned series to *our* agent is done by matching the `instance` label against
the live pod list of the CCP namespace, because cx-1's own control plane shares the `cluster`
label (see §4).

## 8. Conclusion

The `7.2.0-main-07-27-2026-2169504d-ccp` image correctly:

* detects and parses **v1** ConfigMaps, including `controlplane-`-prefixed keys and the flat
  `minimalingestionprofile` setting;
* detects and parses **v2** ConfigMaps, including the `controlplane-metrics` section, the
  v2→v1 key mapping, and the nested `minimal-ingestion-profile: enabled` section;
* **tolerates an incomplete v2 ConfigMap** — a missing optional `prometheus-collector-settings`
  section is skipped with an informational log, and the supplied `controlplane-metrics` values
  are still applied rather than being discarded in favour of defaults (PR #1582 fix confirmed
  present and working);
* honours enable/disable settings end-to-end: only the enabled control-plane jobs are merged into
  the Prometheus config, scraped, and ingested into the Azure Monitor Workspace, with the minimal
  ingestion profile keep-lists applied.

**Recommendation: ✅ approved for release from a CCP ConfigMap-handling standpoint.**
